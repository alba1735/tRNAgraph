# Project Roadmap

This document tracks planned work for tRNAgraph — bugs to fix and features to build — sorted by priority rather than by project phase. It stays forward-looking only: resolved items are removed once done rather than kept as a changelog (see git history for that record). For a technical record of what's already changed and why (statistical methodology differences from tRAX, implementation gotchas that could silently regress), see `improvements_from_trax.md` instead — that document is historical and never has entries removed, the opposite of this one.

### Bugs — Medium Priority

- **Sprinzl acceptor stem labeling is asymmetric and wrong.** `adata.var['location']`'s `loc_dict` (`adataBuild.py`, ~lines 1029-1075) labels the acceptor stem asymmetrically — 5' side `range(-1,8)` vs. 3' side `range(66,77)` — incorrectly folding the discriminator base (73) and CCA tail (74-76) into the stem, plus a phantom `'0'` key that never matches (Sprinzl numbering jumps -1 to 1). Fix: correct the range to the canonical 1-7/66-72 pairing, give the discriminator base and CCA tail their own labels, drop the phantom key. Confirmed isolated to the acceptor stem — D-stem, anticodon-stem, and T-stem are all correctly symmetric already, vetted against canonical Sprinzl numbering (tRAX has no equivalent named-region labeling to diff against, so this is validated against the published numbering scheme instead). Also fix `docs/data_structure.md`'s documented location category names, which don't match any of the actual code strings (stale docs, independent of the range bug). Before finalizing: review how tRNAscan-SE (whose output already feeds `preprocess makedb` directly), tDRnamer, and other Lowe Lab tRNA tools compute and label Sprinzl positions — tRNAgraph's database is built directly from tRNAscan-SE's own output, so drift between the two conventions is a real risk worth ruling out first, and there may be existing position-mapping code/tables worth reusing instead of a from-scratch fix. Validate against canonical Sprinzl numbering and this cross-tool audit rather than a `trna-test` diff against tRAX, since tRAX has no equivalent labeling to diff against. Document the change and its rationale in `improvements_from_trax.md` once implemented.
- **Sprinzl variable-region (e-series) numbering may be semantically wrong.** A known tRAX issue, reported directly by a lab user: the double-digit e-numbers should indicate _paired_ positions and the single-digit e-numbers indicate _unpaired_ loop bases (e.g. e11 pairs with e21; e1 is the first unpaired variable-loop base) — tRNAgraph's `loc_dict`/`toolsGetCoverage.py` per-domain position lists don't currently encode this pairing distinction at all. Whether tRNAgraph's ported code actually inherited tRAX's original issue is **unconfirmed** and needs investigation before scoping a fix. Same cross-tool consistency audit (tRNAscan-SE/tDRnamer/Lowe Lab tools) and validation approach as the acceptor stem fix above applies here too. Related to, but distinct from, the e19→e27 range-extension feature below — **fix the numbering scheme before extending it**, not after, so the extension isn't built on top of a labeling convention about to be redefined.
- **`trim_metadata.tsv` wrong filename for paired-end samples.** `toolsTrim.py`'s `_generate_summary()` writes `{prefix}_merged_trimmed.fastq.gz` as the `fastq` column for every paired-end sample in the auto-generated `trim_metadata.tsv`, but the file fastp (via `_construct_command()`) actually produces is `{prefix}_merged.fastq.gz` (no `_trimmed` in the merged case) — so the auto-generated metadata template points at a file that doesn't exist. `README.md`'s Quick Start example already documents the correct filename convention; check whether anything else in the codebase relies on the wrong name too.
- **`pip install .` (non-editable) fails `tools test`.** CLI commands install and run fine, but the built-in test suite fails because expected assets/directories aren't found — this only resolves correctly under an editable (`-e`) install today. Needs investigation into why, and whether the right fix is packaging the assets properly for a non-editable install or just documenting editable-only as the supported install mode.

### Bugs — Low Priority

- **`embllist` classification tie edge case.** `counttypereads`'s `embllist.getbin(currread)` loop (`toolsCountReads.py`) is set-backed (hash-order-dependent) and does a full-scan max-priority reduction over `ncrnaorder`, rather than first-match-`break`. That reduction is still order-dependent in one narrow case: any `gene_biotype` string outside the 7-item whitelist (`snoRNA`/`miRNA`/`rRNA`/`snRNA`/`misc_RNA`/`lincRNA`/`protein_coding`) defaults to the same priority (0), so if a read overlaps two _different_ unlisted biotypes, `currtype` ends up being whichever one set-iteration happens to visit first. Confirmed unobservable on `test_vibrChol1`'s real GTF (`GCF_000006745.1.gtf`) — it has no `gene_biotype` attribute at all, so every feature falls back to the literal string `"Unknown"`, and a tie between identical strings produces the same result regardless of which one "wins". Needs eukaryotic/human test data with genuine biotype diversity (e.g. Ensembl-style GTFs with `pseudogene`/`antisense_RNA`/etc.) to even verify against, let alone fix.
- **Legacy script cleanup.** None of the 12 `plotsLegacy*.py` files are wired into `cli.py` — they're fully dead/orphaned code today, reachable from nothing. Catalogued disposition:
  - Safe to delete now (fully superseded by a native `plots*.py` module): `plotsLegacyCoverage.py`, `plotsLegacyPCA.py`, `plotsLegacyVolcano.py`, `plotsLegacyLocusCoverage.py`, `plotsLegacyFeatureTypes.py`, `plotsLegacyFeatureTypesReal.py`, `plotsLegacyGeneFeatures.py`.
  - Needs verification before deciding (partial overlap with a native module): `plotsLegacyMismatchBoxplot.py`, `plotsLegacyScatter.py`.
  - Not yet ported (no native equivalent exists) — port to tRNAgraph's own style/conventions, then delete the legacy source: `plotsLegacyReadLength.py` (read-length distribution), `plotsLegacyMismatch.py` (mismatch-count-by-type), `plotsLegacyCCA.py` (3' end/CCA composition). These three overlap with the misincorporation-analysis feature below — scope together when that's picked up, rather than porting these first and redoing them once it lands.
- **Validate VST normalization.** switch default behavior from log1p to VST for that flag, and validate that the VST normalization is working as expected. This is a statistical validation task rather than a code change, but it may require code changes if the current implementation is found to be incorrect or suboptimal.
- **Remove references to MigrationTesting**: This is an internal tool for our own use mentioning it in the offical docs will confuse people. This shows up multiple times in the imrpovements from trax document.
- **logs using --variant flag are not labeled**: Graph/Cluster/etc and other tools that use the variant flag or create splits should have the variant for the run for example right now if cluster is run in a loop for norm:full, norm:u60, norm:o60 all output logs have the same name with the exception of timestamp.
- **reconcile use of the term full, complete and total**: These each have specific definitions in the use of tRNAs (mature/full-length), total reads, complete vs split. Vetting terminiology throughtout the document for consistancy would be ideal making sure it matches best practice for terms via Lowe Lab documentation. A terminology section on data structures would also be helpful for this as well.

## Features / Enhancements

### Features — Medium Priority

- **Sprinzl e-series/variable-arm extension to e27.** e-series variable-arm insertion codes are capped at e19 in both `loc_dict` and the underlying per-domain position lists (`toolsGetCoverage.py`), while canonical class-II tRNAs (e.g. tRNA-Leu, tRNA-Ser) need up to e27 — those variable arms are silently truncated from coverage entirely, a data-completeness gap rather than a labeling bug. The cap exists because a single universal range can't safely cover every domain (Euk/Bact/Archaea already have separate position lists) without misrepresenting some organisms' structures. Planned approach: derive Sprinzl positions dynamically per-species directly from the gtRNAdb file already required for `makedb`'s bowtie2-index build, using the logic from an existing set of Perl scripts (to be incorporated) that always compute the correct Sprinzl positions for a given gtRNAdb — generated alongside the bowtie2 index at database-creation time, so tRNAgraph always has correct e-arm annotations for any given species instead of relying on static per-organism-mode position lists. **Blocked on the numbering/pairing-semantics bug above being resolved first.** Needs its own dedicated design session before implementation, plus real eukaryotic/archaeal test data to validate against actual lab usage (mouse/human/archaea), not just `vibrChol1` — `MigrationTesting`'s `trna-test setup-data` currently only supports `--organism bact`, so extending that is a prerequisite too.
- **Multivariate / timecourse analysis engine.** tRAX only handles one dataset at a time, run repeatedly to build up different views; tRNAgraph is designed for exploring multidimensional experiments instead — the motivating case is a cell-to-organoid timecourse with samples at multiple timepoints, comparing fragment (`u<N>`, e.g. under 60nt) vs. full-length (`o<N>`, e.g. over 60nt) tRNA expression within that design, or more generally any multi-factor design (timepoint, cell type, drug treatment, etc.). **Needs a dedicated design pass before implementation begins** — this scopes the pieces and their dependencies, not the final algorithms. Two prerequisite deliverables: a use-cases doc (not every dataset needs this — single-condition experiments should be unaffected) and config support for declaring category order (e.g. correct chronological timepoint order, since order isn't always inferable from the data itself — see the sample/group ordering feature below, which is this deliverable). This is new statistical code and the highest-risk work on this roadmap — needs test coverage as each piece below lands, rather than retrofitted after the whole feature is "done". Build sequence:
  1. **Fragment vs. full-length comparison (standalone)** — works for any single grouping, independent of study design. Venn diagrams of DE-hit overlap between `u<N>`/`o<N>` splits for a given comparison, using the `venn` PyPI package. A working prototype of the dict-of-sets → `venn()` pattern already exists in `test_organoids/organoid_analysis.ipynb` and should be ported/generalized rather than built from scratch.
  2. **General multi-factor DE engine** (blocks step 3 below) — the current DE machinery is single-factor only: `design_factors="condition"` is hardcoded in the PyDESeq2 build-time path (`adataBuild.py`), and every grouping consumer (PCA colors, volcano groups, `tools log2fc -g`, clustering's hardcoded `grpby='group'`) takes exactly one `adata.obs` column. Build real multi-factor DESeq2 design formulas from N arbitrary `obs` columns (e.g. `~timepoint+celltype`), correctly modeling main effects and interactions rather than collapsing columns into a synthetic composite category, then extend the single-column grouping consumers (plotting, clustering, `log2fc`) to work with it. Also absorbs running arbitrary DESeq2 analyses directly on an existing `.h5ad` as a `tools`-pattern command — the closest existing building block, `adataLog2FC`, has `design_factors` hardcoded to `'condition'`, so a narrowly-scoped standalone version would either be trivial or duplicate this engine.
  3. **Trajectory / decoupling analysis** (needs step 2) — for ordered conditions (timecourse, dose-response), determine whether the frag:full expression ratio changes as the condition changes — e.g. does fragmentation stay proportionally stable across a timecourse, or does it decouple from full-length expression? The same question applies to a simpler two-condition comparison (e.g. drug vs. no drug), not just true timecourses. Model as an interaction term (split × ordered-condition) on top of the multi-factor engine, testable via DESeq2's likelihood ratio test. Exact algorithm/statistical framing deferred to the design pass above.
- **PERMANOVA multivariate statistics.** No multivariate-stats dependency currently exists in the project (no `statsmodels`, no `scikit-bio`). Add `scikit-bio` for PERMANOVA (a cited, maintained implementation preferred over a custom implementation of the stats algorithm; dependency weight is not a concern at this project's scale). Default distance metric: Bray-Curtis, since tRNA count data is zero-heavy and low-count for many features — Euclidean distance is distorted by zero-inflation in this kind of sparse compositional data.
- **Explicit sample/group ordering.** No mechanism currently lets a user specify explicit category order anywhere in tRNAgraph — every plotting module falls back to `sorted()` (alphabetical), and the two existing config files (`--config` filter config, `--colormap`) are transient, per-`graph`-call JSON with no ordering concept. Bake explicit order into `adata.obs` as an ordered `pd.Categorical` at `analyze build` time, so there's a single source of truth reused both for plot legend/axis order and for DESeq2 reference-level ordering, rather than a transient flag that would need to be re-supplied on every plot/DE call (and wouldn't cover the statistics side at all). This is the "category order config" prerequisite deliverable the multivariate engine above depends on.
- **CI/CD test suite coverage.** Currently only `tests/unit/` runs in CI, not `toolsTestSuite.py` or any of the `trna-test` scripts. Will need careful handling of the large, generated `test_vibrChol1/` output directory (gitignored, not checked into the repo). Also incorporate Archaea and Eukaryotic test data into the CI/CD pipeline, since the current `test_vibrChol1/` demo is bacterial-only — `trna-test setup-data` currently only supports `--organism bact`.
- **Mitochondrial tRNA handling.** Mito tRNAs are often very different from nuclear tRNAs and may require special handling in the pipeline. Probably an extra flag at build/map time to perform additional mapping/analysis for mito tRNAs, and/or a separate mito tRNA database — needs consideration of how to handle mito tRNAs in the context of the rest of the pipeline given how different they typically are.
- **Report generation at the end of a pipeline run.** Similar to tRAX's QC report tool — no standalone `trna-report` script actually exists in tRAX, this refers to `traxqc.py`'s `qa.html` output (`ErrorSet`/`SeqPrepInfo`/`MappingResults`/`TypeCount`/`LengthCount`/`TrnaCount`/`SizeFactor` checks). tRNAgraph already has a complete, faithful port of this at `toolsQC.py`, but it was never wired into the CLI or the `analyze build` pipeline — this item is "wire up `toolsQC.py`," not "build a report generator from scratch." Will still need consideration of what to surface for non-technical users (biologists unfamiliar with the CLI/pipeline internals) and how to trigger it (own subcommand vs. automatic post-`build` step).
- **Extend readcutoff/mismatch flags to all graphs.** Volcano's readcutoff flag, and the mismatch flags, should be extended to apply consistently across all graph types rather than just the ones that currently have them.
- **Misincorporation analysis.** Additional misincorporation-analysis code exists already, written outside this repo, and is planned to be incorporated here. Overlaps with the still-unported `plotsLegacyMismatch.py`/`plotsLegacyMismatchBoxplot.py` (see Legacy script cleanup above) — scope both together when this is picked up, rather than porting the legacy mismatch plots first and redoing them once the new analysis lands. Includes a `--filtermismatches` graph-time flag (research this as part of scoping the new mismatch graphs themselves, not before building it in isolation) — unrelated to `--maxmismatches` despite the similar name: `--maxmismatches` (`analyze build`) is a read-level QC exclusion filter (a too-noisy read never gets counted into anything; once applied, individual read records are gone, so it can't be reproduced or reversed at graph time from stored data alone). A `--filtermismatches`-style flag would instead be a graph-time _selection/display_ filter operating on the mismatch rate already stored per position (`mismatchedbases`/`coverage` in `adata.var`/`X`) — analogous to `toolsGetCoverage.py`'s existing `sigmismatch`/`mismatchthreshold=0.05` mechanism (which positions/genes to highlight, not which reads to count).

### Features — Low Priority

- **Automatic/curated gtRNAdb database creation.** Automatic gtRNAdb db creation, or a curated list of pre-built dbs for common organisms (e.g. human, mouse, E. coli, S. cerevisiae, etc.), to avoid the need for users to build their own dbs.
- **Modification analysis.** Dependent on sequencing type and species, so it will need to be a separate module only run when the user has the correct data type and organism. A long-term goal requiring more research and development.
- **SINE handling.** Mouse/Rat have tons of SINEs that are tRNA-derived, which caused problems in tRAX and will likely cause problems in tRNAgraph too. tRAX's workaround was using gtRNAdb's High Confidence tRNA set, which isn't a perfect solution — some dedicated SINE analysis might be worth exploring.
- **Hub generation improvements.** Explore whether track hub generation can be nicer and based on config/colormaps etc.; multitrack BAM support would also be ideal.
- **Google Colab notebook / tutorial.** For new users to run through the pipeline without installing anything locally. An existing tRAX Colab notebook can be used as a guideline, updated for tRNAgraph's CLI and features.
- **Reporter Discord/Slack/Other Bot.** A bot that can report on the status of a run, or alert when a run is complete, or when a run fails. Could be useful for long-running jobs on a cluster or cloud environment.
- **GUI.** A GUI for tRNAgraph would be a long-term goal, but not a priority at this time. It would require significant development and design work, and is not necessary for the core functionality of the pipeline.
