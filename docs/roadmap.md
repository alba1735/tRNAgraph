# Project Roadmap

This document tracks planned work for tRNAgraph — bugs to fix and features to build — sorted by priority rather than by project phase. It stays forward-looking only: resolved items are removed once done rather than kept as a changelog (see git history for that record). For a summary of what already changed relative to tRAX, see `improvements_from_trax.md`.

## Bugs / Fixes

### Bugs — Medium Priority

- **A GTF whose chromosome names don't match the genome fails silently.** `toolsTG.readgtf` takes the chromosome straight from `fields[0]` with no validation, and features are then looked up per-chromosome against the mapped reads, so a GTF using Ensembl-style names (`1`, `2`, `MT`) against a UCSC-style genome (`chr1`, `chr2`, `chrM`) — or the reverse — matches nothing at all. Nothing in the codebase compares the two name sets. The result is not an error but a run in which every non-tRNA feature count is zero: the tRNA side of the pipeline is driven by the tRNAscan-SE/gtRNAdb database rather than the GTF and so looks entirely healthy, while the non-tRNA volcano/PCA panels quietly disappear. The only user-visible signal is graph-time's "No non-tRNA feature counts found in AnnData object … Re-run `trnagraph analyze build` with `--gtf` to enable these" (`toolsTG.py`), which actively misdirects, since `--gtf` _was_ supplied and the real fault is the naming scheme. Mixing sources this way is easy to do by accident because the two common reference hosts disagree: UCSC/ENCODE genomes use `chr`-prefixed names and Ensembl GTFs do not. Fix: at `analyze build`, intersect the GTF's chromosome names against the reference names present in the BAM headers and refuse (or at minimum warn loudly, naming both spellings) when the overlap is empty. Note this is distinct from the legitimate zero-count case described under "Mitochondrial tRNA handling" below — there the reference genuinely lacks the features; here the features exist and are unreachable — so the check must distinguish "no overlap at all" from "some features have no reads".
- **Two organism position tables are offset against their own covariance models.** Verified by emitting each shipped mature covariance model's consensus structure (`cmemit -a`) and aligning paired/unpaired columns against `toolsGetCoverage.POSITION_TABLES`. `euk` is correct: the variable arm reads 7 paired, 5 unpaired, 7 paired, and 44/46/47/48 are unpaired as they should be. `bact` is not — the column labelled `46` is base-paired, but 46 is a variable-**loop** position and must be unpaired, so that column is really the last variable-stem position and the table is off by one at the 3' boundary. `arch` is worse: 44, 45 and 46 are all paired and the two stem sides come out 6 against 7, which is structurally impossible for a stem, so it is offset at the 5' boundary too. Read counts are unaffected — this mislabels axis positions, not values — but `bact` is the mode the demo dataset and CI actually run on. Cannot be fixed by hand: pairing alone cannot decide which of 46/47/48 the surviving unpaired columns are, which is precisely what the Sprinzl mapper below computes. **Blocked on that port.** Note the related e-series pairing question is now _settled_, not open: double-digit e-codes are the paired variable-stem positions (e11 with e21, e12 with e22, … e17 with e27) and single digits e1–e5 the unpaired loop bases, confirmed against tRNAscan-SE's own `SprinzlPos.pm`.

### Bugs — Low Priority

- **`arch` and `mito` organism modes are unvalidated.** Their Sprinzl position tables match tRAX byte for byte, but no run has ever exercised either mode end to end: `bact` is the only mode with automated coverage and `euk` is only reached by a large human dataset that does not run in CI. This is not merely a table lookup — `toolsGetCoverage.main()` branches on `orgtype != "euk"` to decide whether position numbers come from a numbers file or are derived from the alignment, so the two sides are genuinely different code paths and a defect in one is invisible from the other. Both bugs found while validating the human dataset (multi-mapped reads in coverage, and the pre-tRNA edge margin applied twice) lived on the alignment-derived side and so were invisible to the bacterial suite. Lowered to low priority pending test data: representative archaeal and mitochondrial tRNA sets need sourcing first. Related to the "Mitochondrial tRNA handling" feature below, which is the larger piece of work — mito tRNAs are absent from the default reference set by design, since gtRNAdb and tRNAscan-SE exclude them, so validating that mode needs a database that contains them. The long-term goal is a pipeline robust across all tRNAs rather than one validated only where the test data happens to be.
- **`embllist` classification tie edge case.** `counttypereads`'s `embllist.getbin(currread)` loop (`toolsCountReads.py`) is set-backed (hash-order-dependent) and does a full-scan max-priority reduction over `ncrnaorder`, rather than first-match-`break`. That reduction is still order-dependent in one narrow case: any `gene_biotype` string outside the 7-item whitelist (`snoRNA`/`miRNA`/`rRNA`/`snRNA`/`misc_RNA`/`lincRNA`/`protein_coding`) defaults to the same priority (0), so if a read overlaps two _different_ unlisted biotypes, `currtype` ends up being whichever one set-iteration happens to visit first. Confirmed unobservable on `test_vibrChol1`'s real GTF (`GCF_000006745.1.gtf`) — it has no `gene_biotype` attribute at all, so every feature falls back to the literal string `"Unknown"`, and a tie between identical strings produces the same result regardless of which one "wins". Needs eukaryotic/human test data with genuine biotype diversity (e.g. Ensembl-style GTFs with `pseudogene`/`antisense_RNA`/etc.) to even verify against, let alone fix.
- **Legacy script cleanup.** Three `plotsLegacy*.py` files remain, none wired into `cli.py`. Catalogued disposition:
  - Needs verification before deciding (partial overlap with a native module): `plotsLegacyScatter.py`.
  - Not yet ported (no native equivalent exists) — port to tRNAgraph's own style/conventions, then delete the legacy source: `plotsLegacyReadLength.py` (read-length distribution), `plotsLegacyCCA.py` (3' end/CCA composition). Both overlap with the misincorporation-analysis feature below — scope together when that's picked up, rather than porting these first and redoing them once it lands.
- **Validate VST normalization.** switch default behavior from log1p to VST for that flag, and validate that the VST normalization is working as expected. This is a statistical validation task rather than a code change, but it may require code changes if the current implementation is found to be incorrect or suboptimal.
- **reconcile use of the term full, complete and total**: These each have specific definitions in the use of tRNAs (mature/full-length), total reads, complete vs split. Vetting terminiology throughtout the document for consistancy would be ideal making sure it matches best practice for terms via Lowe Lab documentation. A terminology section on data structures would also be helpful for this as well.
- **`--allreads` produces a duplicate PCA output directory at default settings.** `plotsPca.OVERVIEW_TRNA_READTYPES` pins the both-bases comparison so it survives whatever `--pcareadtypes` asks for, which means that with the default `--pcareadtypes total` a default run and an `--allreads` run emit exactly the same two files — one into `pca/`, the other into `pca/allreads/`. They only diverge once `--pcareadtypes` names something beyond `total`. This is at odds with the output-layout convention that a directory names what was plotted rather than which flags were typed (which is why coverage has no `allreads/` segment at all). Options are to make the basis segment conditional on the resolved readtype sets actually differing, or to accept the duplication as the cost of guaranteeing the comparison. Low priority because PCA is cheap to regenerate, unlike coverage, where the same duplication would have been expensive enough to matter.
- **vet combined_trna_specificty plot against tRAX**: the legend placement is fixed (it was anchored to the figure corner rather than to the subplot grid, leaving it stranded above the plots). What remains is the substantive half — comparing the rendered plot against tRAX's coverage output by eye to confirm the two tell the same story, which needs a human looking at both.

## Features / Enhancements

### Features — High Priority

- **Adata Version Check**: On graphing/cluster and other upstream of build tools check adata version against breaking changes, give warning that it might fail if adata isn't updated and offer to try an update in-place (temp folder then copy over if success) using runinfo.

### Features — Medium Priority

- **Emit all-feature-normalized count outputs.** `results/<variant>/allfeature/` currently holds only the DESeq2 products (size factors, normalized read counts, medians, dispersions, averages). The count outputs that tRAX size-factor-normalizes -- `typecounts`, `coverage`, `mismatches` -- exist only in their primary, tRNA-controlled-normalized form, so there is no tRNAgraph file directly comparable to the equivalent from a tRAX run driven by all-feature size factors. This makes the parity check against tRAX's real-GTF run scale-shifted rather than direct: the offset is provably just the ratio of the two size-factor sets (matching to within 0.3-2.6% on the human dataset), but it has to be reasoned around every time rather than simply diffed. Emitting all-feature-normalized counterparts alongside the existing ones would close that, and would also give users the non-tRNA-inclusive normalization view that tRAX's real-GTF run provides.
- **Port the per-species Sprinzl position mapper into `makedb`.** Supersedes what was described here as an "extension to e27" — that framing was wrong. The canonical e-series is e1–e5, e11–e17 and e21–e27, which is 19 codes, and `eukpositions` already carries 19 e-slots: nothing is truncated, the same columns are simply mislabelled `e1…e19`. The real fix is to stop relying on static per-organism-mode tables at all and derive positions per species, per tRNA, at database-build time. The reference implementation is Patricia Chan's `tRNA_sprinzl_pos` (tRNAscan-SE Perl modules): it aligns each tRNA with `cmalign` and maps alignment columns to Sprinzl codes, and its `SprinzlAlignResults` already has a `write_sprinzl_pos_db()` that emits every tRNA into one `//`-delimited file — a database artefact ready-made for `makedb`. This also fixes the `bact`/`arch` table offset above, and gives correct variable-arm annotation for class-II tRNAs of any species rather than whichever domain the static tables happen to suit. Four gaps to design around: (1) no mitochondrial clade — the tool's config defines covariance models for eukaryota/archaea/bacteria only, so `mito` stays on static tables; (2) the mapping is bound to that tool's own covariance models, which differ from tRNAgraph's shipped copies (its `TRNAinf-euk.cm` is `CLEN 98` against tRNAgraph's `CLEN 95`), so the matched models must be ported alongside the logic and cannot be substituted; (3) it consumes a tRNAscan-SE `-detailed.ss` file, which `makedb` does not currently take — it takes the `.out`; (4) it is Perl, so porting means adding a runtime dependency or reimplementing the alignment column mapping in Python (the position/region tables themselves port trivially). Needs its own design session, plus eukaryotic/archaeal test data to validate against — the shared test-data setup is bacterial-only today. Confirmed _not_ a blocker: tRNAgraph's static tables are correctly matched to the mature models it ships (`trnamature-euk.cm` `CLEN 99` against 99 euk positions; arch/bact/mito likewise).
- **Finish porting tRAX's `mismatch/` plot set.** `graph -g mismatch` (`plotsMismatch.py`) currently covers 3 of the 17 plot families tRAX writes into `mismatch/`, plus two tRNAgraph additions (an overview deletions plot and the read-level histogram). Measured against the bacterial demo run (22 amino acids, 93 positions), what is ported is the position-misincorporation overview (tRAX's `trnapositionmismatches.pdf`), its per-amino counterparts (`<amino>_trnapositionmismatches.pdf`), and `sigmismatch.txt`. What is not:
  - **Per-amino heatmaps** (4 families, 22 files each): `<amino>_mismatchheatmap.pdf`, `<amino>_deletionheatmap.pdf`, `<amino>_fiveprimeheatmap.pdf`, `<amino>_threeprimeheatmap.pdf` — all from `boxplotmismatches.R`. These are the most obviously missing pieces, since a heatmap over position × tRNA is the natural way to read a whole amino-acid family at once and nothing in tRNAgraph currently renders one for mismatch data.
  - **Per-amino end/percent plots** (5 families, 22 files each): `<amino>_fiveprimecounts.pdf` and `<amino>_threeprimecounts.pdf` from `boxplotmismatches.R`; `<amino>_mismatch.pdf`, `<amino>_delete.pdf` and `<amino>_fiveprimeends.pdf` from `newcoverageplots.R`'s `makepercentcovplot()`. Note the last three are written into `mismatch/` by the _coverage_ script, so scoping this needs a decision on whether they belong to the mismatch module or to `plotsCoverage.py`, which already owns percent-coverage rendering.
  - **Per-position breakdowns** (5 families, 93 files each — 465 files): `<pos>_possamplemismatches.pdf`, `<pos>_possampledeletions.pdf`, `<pos>_possamplereadstarts.pdf`, `<pos>_posaminomismatches.pdf`, `<pos>_posaminodeletions.pdf`, all from `boxplotmismatches.R`. Emitting 465 individual files would be at odds with the output-layout convention; a multi-page roll-up per family (as `combined_positionmismatches_by_amino.pdf` already does) is the better shape, with individual files under `individual/` only if a user asks for them.
  - **`trnapositionfiveprime.pdf`** — deliberately skipped rather than missed: `plotsCoverage.py` already renders `readstarts`/`readends` from the same object, and duplicating it here would put one picture in two directories. Revisit only if the mismatch-specific framing turns out to say something the coverage plot doesn't.

  Scope with the misincorporation-analysis entry below rather than porting family-by-family: several of these are the same data under different aggregations, so deciding the aggregation vocabulary once is cheaper than porting 17 scripts. The data all of them need is already in the AnnData object (`mismatchedbases`, `deletedbases`, `readstarts`, `readends`, `deletions` and the per-base coverage types), so none of this is blocked on a rebuild or a new output file.

- **Multivariate / timecourse analysis engine.** tRAX only handles one dataset at a time, run repeatedly to build up different views; tRNAgraph is designed for exploring multidimensional experiments instead — the motivating case is a cell-to-organoid timecourse with samples at multiple timepoints, comparing fragment (`u<N>`, e.g. under 60nt) vs. full-length (`o<N>`, e.g. over 60nt) tRNA expression within that design, or more generally any multi-factor design (timepoint, cell type, drug treatment, etc.). **Needs a dedicated design pass before implementation begins** — this scopes the pieces and their dependencies, not the final algorithms. Two prerequisite deliverables: a use-cases doc (not every dataset needs this — single-condition experiments should be unaffected) and config support for declaring category order (e.g. correct chronological timepoint order, since order isn't always inferable from the data itself — see the sample/group ordering feature below, which is this deliverable). This is new statistical code and the highest-risk work on this roadmap — needs test coverage as each piece below lands, rather than retrofitted after the whole feature is "done". Build sequence:
  1. **Fragment vs. full-length comparison (standalone)** — works for any single grouping, independent of study design. Venn diagrams of DE-hit overlap between `u<N>`/`o<N>` splits for a given comparison, using the `venn` PyPI package. A working prototype of the dict-of-sets → `venn()` pattern already exists in `test_organoids/organoid_analysis.ipynb` and should be ported/generalized rather than built from scratch.
  2. **General multi-factor DE engine** (blocks step 3 below) — the current DE machinery is single-factor only: `design_factors="condition"` is hardcoded in the PyDESeq2 build-time path (`adataBuild.py`), and every grouping consumer (PCA colors, volcano groups, `tools log2fc -g`, clustering's hardcoded `grpby='group'`) takes exactly one `adata.obs` column. Build real multi-factor DESeq2 design formulas from N arbitrary `obs` columns (e.g. `~timepoint+celltype`), correctly modeling main effects and interactions rather than collapsing columns into a synthetic composite category, then extend the single-column grouping consumers (plotting, clustering, `log2fc`) to work with it. Also absorbs running arbitrary DESeq2 analyses directly on an existing `.h5ad` as a `tools`-pattern command — the closest existing building block, `adataLog2FC`, has `design_factors` hardcoded to `'condition'`, so a narrowly-scoped standalone version would either be trivial or duplicate this engine.
  3. **Trajectory / decoupling analysis** (needs step 2) — for ordered conditions (timecourse, dose-response), determine whether the frag:full expression ratio changes as the condition changes — e.g. does fragmentation stay proportionally stable across a timecourse, or does it decouple from full-length expression? The same question applies to a simpler two-condition comparison (e.g. drug vs. no drug), not just true timecourses. Model as an interaction term (split × ordered-condition) on top of the multi-factor engine, testable via DESeq2's likelihood ratio test. Exact algorithm/statistical framing deferred to the design pass above.
- **Release-channel selection for `update` (`--mode stable|dev|nightly`).** `trnagraph update` exposes git mechanics rather than release channels: `--branch` defaults to whichever branch happens to be checked out, and `--tag` requires the user to already know the exact release number, so there is no way to ask for "the newest stable release" without looking it up. Proposed: `--mode stable|dev|nightly` as the documented front door — `stable` resolving to the highest non-prerelease tag, `dev` to the highest prerelease tag, `nightly` to the head of `dev` — with `--branch`/`--tag` kept as escape hatches, `--tag` in particular because pinning a specific historical release is what reproducing a published analysis requires. Two things need settling in a design pass before implementation. First, the channel _labels_ are wrong today for a related reason: `env_check.get_version_channel()` maps the `dev` branch to `prerelease`, but many commits share one `__version__` between version bumps, so every one of them reports identically — being _on_ `dev` is honestly `nightly @ <hash>`, and `prerelease` should mean a detached checkout at an actual prerelease tag. Second, `dev` mode has no artifact to resolve to yet: `pyproject.toml` configures `dev` as an `-alpha.N` prerelease channel, but no prerelease tag has ever been cut, so either the release workflow starts publishing them (in which case prereleases must be kept from archiving on Zenodo as citable releases) or the feature ships with `stable`/`nightly` only until it does.
- **PERMANOVA multivariate statistics.** No multivariate-stats dependency currently exists in the project (no `statsmodels`, no `scikit-bio`). Add `scikit-bio` for PERMANOVA (a cited, maintained implementation preferred over a custom implementation of the stats algorithm; dependency weight is not a concern at this project's scale). Default distance metric: Bray-Curtis, since tRNA count data is zero-heavy and low-count for many features — Euclidean distance is distorted by zero-inflation in this kind of sparse compositional data.
- **Explicit sample/group ordering.** No mechanism currently lets a user specify explicit category order anywhere in tRNAgraph — every plotting module falls back to `sorted()` (alphabetical), and the two existing config files (`--config` filter config, `--style`) are transient, per-`graph`-call JSON with no ordering concept. Bake explicit order into `adata.obs` as an ordered `pd.Categorical` at `analyze build` time, so there's a single source of truth reused both for plot legend/axis order and for DESeq2 reference-level ordering, rather than a transient flag that would need to be re-supplied on every plot/DE call (and wouldn't cover the statistics side at all). This is the "category order config" prerequisite deliverable the multivariate engine above depends on.
- **CI/CD test suite coverage.** Currently only `tests/unit/` runs in CI, not `toolsTestSuite.py` or the end-to-end validation scripts. Will need careful handling of the large, generated `test_vibrChol1/` output directory (gitignored, not checked into the repo). Also incorporate Archaea and Eukaryotic test data into the CI/CD pipeline, since the current `test_vibrChol1/` demo is bacterial-only.
- **Mitochondrial tRNA handling.** Mito tRNAs are often very different from nuclear tRNAs and may require special handling in the pipeline. Note that they are absent from the default reference set by design, not by oversight: gtRNAdb and tRNAscan-SE do not include mitochondrial tRNAs by default, so a database built by `preprocess makedb` contains only nuclear-encoded tRNAs. This holds even when the GTF passed to `--gtf` does contain mitochondrial entries, because the tRNA side of the pipeline is driven by the tRNAscan-SE/gtRNAdb-derived database rather than by the GTF -- which is why a human dataset can legitimately report `Mt_tRNA` and `Mt_rRNA` counts of zero without anything being broken. Supporting them therefore needs a deliberate change at database-build time: probably an extra flag at build/map time to perform additional mapping/analysis for mito tRNAs, and/or a separate mito tRNA database, plus consideration of how to handle them in the context of the rest of the pipeline given how different they typically are. One concrete dependency already exists: read-length split variants exclude non-tRNA GTF features, and the `Mt_tRNA` **type** row is deliberately kept on the tRNA side of that filter (`TRNA_TYPE_LABELS` in `adataBuild.py`) so the data keeps flowing rather than being dropped now and re-added later. The **feature**-level filter is a different matter: it uses a name-based predicate (`toolsTG.is_trna_feature`, matching `tRNA`/`tRX` in the feature name), which today is moot because a `makedb` database contains no mitochondrial tRNAs at all. Once they are first-class they will arrive as GTF-named features (e.g. Ensembl gene IDs) that predicate will not match, so it — and its shared use for DESeq2 size-factor control genes — needs revisiting as part of this work, not after it.
- **Report generation at the end of a pipeline run.** Similar to tRAX's QC report tool — no standalone `trna-report` script actually exists in tRAX, this refers to `traxqc.py`'s `qa.html` output (`ErrorSet`/`SeqPrepInfo`/`MappingResults`/`TypeCount`/`LengthCount`/`TrnaCount`/`SizeFactor` checks). tRNAgraph already has a complete, faithful port of this at `toolsQC.py`, but it was never wired into the CLI or the `analyze build` pipeline — this item is "wire up `toolsQC.py`," not "build a report generator from scratch." Will still need consideration of what to surface for non-technical users (biologists unfamiliar with the CLI/pipeline internals) and how to trigger it (own subcommand vs. automatic post-`build` step).
- **Extend readcutoff/mismatch flags to all graphs.** Volcano's readcutoff flag, and the mismatch flags, should be extended to apply consistently across all graph types rather than just the ones that currently have them.
- **Misincorporation analysis.** Additional misincorporation-analysis code exists already, written outside this repo, and is planned to be incorporated here. The legacy mismatch plots are partly ported and live at `plotsMismatch.py` (`graph -g mismatch`), so this feature extends that module rather than starting from the R scripts — see "Finish porting tRAX's `mismatch/` plot set" above for exactly what is and isn't covered, and scope the two together. Includes a `--filtermismatches` graph-time flag (research this as part of scoping the new mismatch graphs themselves, not before building it in isolation) — unrelated to `--maxmismatches` despite the similar name: `--maxmismatches` (`analyze build`) is a read-level QC exclusion filter (a too-noisy read never gets counted into anything; once applied, individual read records are gone, so it can't be reproduced or reversed at graph time from stored data alone). A `--filtermismatches`-style flag would instead be a graph-time _selection/display_ filter operating on the mismatch rate already stored per position (`mismatchedbases`/`coverage` in `adata.var`/`X`) — analogous to `toolsGetCoverage.py`'s existing `SIGMISMATCH_BED_THRESHOLD` mechanism (which positions/genes to highlight, not which reads to count), and adjacent to the existing graph-time `--mismatchpseudocount`.

### Features — Low Priority

- **Long-term validation against a large human dataset.** The `hg38` organoid dataset used to find and fix the pipeline-failure bugs lives outside the repo because of its size, and its BAM/FASTQ files cannot realistically be regenerated on a development machine — treat the copy as read-only and never re-trim or re-map it in place. Once the data is published to GEO it can be fetched on demand, which would let a eukaryotic end-to-end check run periodically rather than only when someone has the files to hand, and would give a basis for estimating the compute a dataset of that scale needs. Subsetting it for faster repeat testing is reasonable provided the originals are never overwritten.
- **Unify the console experience between the main commands and `tools test`.** `trnagraph tools test` renders a live cyan "Recent activity" panel with an overall progress bar (`toolsTestSuite.py`'s `Panel(...)`, the only `Panel` in the codebase), while the main commands show only `toolsTG.progress_iterator`'s green spinner/bar — and only during the five phases that wrap a per-item loop (`Trimming samples`, `Mapping samples`, `Counting reads`, `Coverage plots`, `Graphing`), with plain log lines everywhere else. This is a design difference, not a defect: the test suite's box wraps _subprocess_ invocations and drives itself by parsing their `"<desc> phase N/Total (P%) complete"` output, whereas `PhaseTracker` is documented as "deliberately NOT a rich `Live`/spinner owner". Giving `analyze build`/`graph` an equivalent whole-run panel means making `PhaseTracker` own a `Live` display and coordinating it with `progress_iterator`'s inner display so the two don't contend for the terminal — the reason they were kept separate originally. Any implementation must keep the existing non-TTY fallback intact: the milestone lines are what the test suite parses, and what makes a redirected or piped run readable in a log file.
- **Automatic/curated gtRNAdb database creation.** Automatic gtRNAdb db creation, or a curated list of pre-built dbs for common organisms (e.g. human, mouse, E. coli, S. cerevisiae, etc.), to avoid the need for users to build their own dbs.
- **Modification analysis.** Dependent on sequencing type and species, so it will need to be a separate module only run when the user has the correct data type and organism. A long-term goal requiring more research and development.
- **SINE handling.** Mouse/Rat have tons of SINEs that are tRNA-derived, which caused problems in tRAX and will likely cause problems in tRNAgraph too. tRAX's workaround was using gtRNAdb's High Confidence tRNA set, which isn't a perfect solution — some dedicated SINE analysis might be worth exploring.
- **Hub generation improvements.** Explore whether track hub generation can be nicer and based on config/colormaps etc.; multitrack BAM support would also be ideal.
- **Google Colab notebook / tutorial.** For new users to run through the pipeline without installing anything locally. An existing tRAX Colab notebook can be used as a guideline, updated for tRNAgraph's CLI and features.
- **Reporter Discord/Slack/Other Bot.** A bot that can report on the status of a run, or alert when a run is complete, or when a run fails. Could be useful for long-running jobs on a cluster or cloud environment.
- **GUI.** A GUI for tRNAgraph would be a long-term goal, but not a priority at this time. It would require significant development and design work, and is not necessary for the core functionality of the pipeline.
- **Unify and improve the default color scheme.** Every color tRNAgraph draws with now lives in `modules/plotsPalette.py`, named by role (`DE_UP`, `SEQUENTIAL_SIGNIFICANCE`, `ARM_STEM`, `REFERENCE_LINE`, ...) rather than by appearance, and a test rejects any new hex literal or direct `husl_palette()` call in a plot module — so this work is now a matter of retuning values in one file rather than hunting literals across twelve. Two things to settle when it is picked up. **Accessibility**: the current categorical fallback is seaborn's `husl`, which is not colorblind-safe at higher category counts; a perceptually-uniform, colorblind-safe qualitative set is the obvious replacement, but the count of simultaneously-distinguishable categories is the real constraint (some plots colour by amino acid, i.e. ~22 categories, where no qualitative palette works and the answer is probably to stop colouring by that dimension). **Consistency**: three different sequential ramps are in use (`Blues` for correlation and seqlogo scores, `Greens` for significance, `Greys` for sequence, `mako_r` for ordered specificity) — some of that is deliberate (they encode different quantities and should not be confusable) and some is historical, and the two need separating before anything is changed.
- **Lite Graph Flag**: Option to quickly generate combined plots rather than all plots this can increase time dramatically with coverage and some other options for a quick output.
- **tRAX Conversion Tool**: Tool to convert tRAX input files to tRNAgraph manifest/metadata etc.
- **bioconda/pypi release**: Make installing easier by making it a conda tool and python release.

## Notes for Contributors

PyDESeq2 and AnnData carry several gotchas relevant to any code that constructs `DeseqDataSet`s or touches AnnData slots — most directly relevant to the multivariate engine above. See the project's internal implementation notes before writing such code.
